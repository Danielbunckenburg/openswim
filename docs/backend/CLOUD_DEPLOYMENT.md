## Cloud setup

1. Sign in to a Supabase organization with MFA. The chosen project is in the **specific EU region** `eu-central-1` (Frankfurt). Record its database password in a password manager, never in Git. A broad `Europe` region is not a substitute for selecting an EU jurisdiction: [Supabase regions](https://supabase.com/docs/guides/platform/regions).
2. Authenticate the CLI locally with `supabase login`, then link this repository with `supabase link --project-ref <project-ref>`. For an existing project, inspect its current schema and migration history before applying OpenSwim's migration. A new, empty project is the simplest target.
3. For future migrations, preview with `supabase db push --dry-run`, then apply with `supabase db push` after checking the target project. **Do not** pass `--include-seed` or use `db reset --linked`: `supabase/seed.sql` contains fictional local users and workouts. See the [Supabase CLI workflow](https://supabase.com/docs/guides/local-development/cli-workflows).
4. Run the read-only `supabase/tests/cloud_smoke.sql` after schema changes, for example with `supabase db query --linked --file supabase/tests/cloud_smoke.sql`. Inspect grants and policies in the Dashboard Security Advisor too. Keep the service-role key and database password out of Android, Wear, Git, and logs.

## Auth and Android connection

- **Temporary Auth state (25 September 2026):** `auth.email.enable_confirmations = false` and `auth.enable_signup = true` on the hosted project, at the owner's request. Any visitor can create an account and sign in immediately without proving control of the email address. The Android `0.2.0-test` build handles the signup response's active session. A live signup, password sign-in, and authenticated database read all returned HTTP 200. Before relying on email identity or inviting broader real users, configure a custom SMTP provider, test confirmation and password reset, then re-enable email confirmations. Supabase's default mail service only delivers to authorized team addresses: [SMTP guidance](https://supabase.com/docs/guides/auth/auth-smtp), [Auth configuration](https://supabase.com/docs/guides/auth/general-configuration).
- The Android build reads `supabase.url` and `supabase.publishableKey` from ignored `local.properties`. The workspace is configured for this cloud project with its **publishable key only**. For another checkout, add those two properties from the Supabase dashboard before building. They are client configuration, not database credentials. Keep the service-role/secret key server-side.
- The app supports email/password sign-in and account creation. The cloud project's allowed redirect list includes `org.openswim.android://auth/callback`, and the Android activity handles that confirmation link when confirmation is restored. The cloud Auth site URL is the published web app, while Android sign-up explicitly requests its own callback. See [redirect URL guidance](https://supabase.com/docs/guides/auth/redirect-urls).
- The web app at `website/app.html` uses the same publishable key and each user's Auth session. The allowed redirect list also includes `https://danielbunckenburg.github.io/openswim/app.html` and `http://localhost:8000/app.html` for local testing. Web accounts can create workouts and plans, schedule a swim, log a completed swim, and edit profile preferences; the same rows are then visible to the Android client under the same account. The website is served as static files through GitHub Pages, so only the publishable key is present in `website/config.js`.
- Test cloud Auth with controlled test accounts, then repeat owner, cross-user, public, and private REST checks before shipping the Android adapter. The local Mailpit automation cannot confirm email on the hosted project; use a real test inbox after SMTP is configured.
